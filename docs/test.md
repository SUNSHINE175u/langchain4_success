RESTful Web 服务是一种基于 \*\*REST（表述性状态转移）\*\* 架构风格构建的轻量级 Web 服务。它并非一个严格的标准，而是一组设计约束，核心思想是将数据和功能视为“资源”，并通过标准的 Web 接口（通常是 HTTP）来操作这些资源。



\### 核心概念：资源与操作



RESTful 服务的设计围绕“资源”展开。每个资源（如一个用户、一篇文章）都通过一个唯一的 \*\*URI（统一资源标识符）\*\* 来标识，例如 `/users/123`。客户端通过标准的 HTTP 方法对资源执行操作，这恰好对应了数据的增删改查：



| HTTP 方法 | 操作含义 | 示例（针对 `/users/123`） |

| :--- | :--- | :--- |

| \*\*GET\*\* | 获取资源 | 获取用户 123 的信息 |

| \*\*POST\*\* | 创建新资源 | 在 `/users` 上提交数据以创建新用户 |

| \*\*PUT\*\* | 更新（或替换）资源 | 用新数据完全替换用户 123 的信息 |

| \*\*DELETE\*\* | 删除资源 | 删除用户 123 |



例如，访问 `GET /accounts` 会返回所有账户列表，而 `GET /accounts/1` 则返回账户 1 的详细信息。



\### 关键架构约束



要被称为“RESTful”，服务通常需要遵循以下几项关键约束：



\*   \*\*无状态性\*\*：这是最重要的原则之一。服务器不会在两次请求之间保存客户端的任何状态（会话信息）。每个请求都必须包含服务器理解并处理它所需的全部信息。这使得服务更可靠、更易于扩展。

\*   \*\*统一接口\*\*：所有资源都通过同一套标准方法（如上述的 HTTP 方法）来访问，简化了系统架构。

\*   \*\*可缓存\*\*：响应应明确标识其是否可被缓存。客户端或中间层可以缓存响应，以减少对服务器的请求次数，提升性能。

\*   \*\*分层系统\*\*：客户端无需知道它是直接连接到最终服务器，还是通过中间层（如代理、网关）连接。这有助于通过负载均衡等方式提升系统可扩展性。



\### 与 SOAP 的简要对比



与另一种常见的 Web 服务风格 SOAP 相比，RESTful 服务通常被认为更\*\*轻量、简单\*\*。它直接利用 HTTP 协议本身的能力，而不需要像 SOAP 那样依赖额外的消息层和复杂的 XML 信封。RESTful 服务返回的数据格式灵活，常见的有 JSON 或 XML，这使得它非常适合构建面向互联网的 API。



结合你之前翻译的内容，Spring 中的 `@RestController` 正是用于简化构建这类 RESTful 服务，它会自动将方法返回的对象（如 `Greeting`）通过消息转换器（如 Jackson）序列化为 JSON 并写入 HTTP 响应体，这正是 RESTful 风格中“资源表述”的体现。
